# 伏线工程可迁移与开箱体验升级实施计划

> 执行交接：按任务逐项实现和验收；独立任务在独立 Git 工作树并行推进，最后统一集成。

**目标：** 用户关闭重开、换浏览器或换安装目录后能找回上次工程；收到 `.fuxian` 的人能找到打开入口并离线重跑；需要 AI 时用自己的客户端和路径完成连接。

**架构：** 安装目录负责启动程序和运行资源；每个 Windows 用户有独立的本机工程库，负责自动保存和恢复；`.fuxian` 是给他人的交换文件；AI 连接配置由接收方根据自己的环境生成。三者通过明确的接口关联。

**技术栈：** React、TypeScript、本机 Node 服务、Windows 图形启动器、`.fuxian` v1 ZIP、MCP stdio、ngspice。基线为公开 v0.30.5，提交 `8c48183`。

## 1. 现状与决策

| 用户遇到的情况 | v0.30.5 已核对的行为 | 决策 |
| --- | --- | --- |
| 软件重开后工程不见 | `src/App.tsx` 将工程存进浏览器 `localStorage`，同一浏览器资料和站点下已有“恢复选中工程”逻辑。换浏览器、浏览器资料、端口或 `localhost`/`127.0.0.1` 会读到不同的存储空间。此为一条已确认的代码路径，尚未定位用户电脑每次消失的具体触发条件。 | 以本机工程库为主；优先守住已有数据，再修启动恢复。 |
| 打开工程不明显，“另存”反而占一整行 | `src/components/ProjectSidebar.tsx` 把“另存副本”放在整行操作区，“打开工程文件”在两列小按钮内，`src/project-sidebar.css` 为它设置了 30 px 最小高度和 10 px 字。顶栏入口藏在“文件”中。 | 顶栏保留带文字的“打开工程”；项目栏首屏同样可见；“另存副本”移至项目菜单。 |
| 发给别人仍要找库和配目录 | `.fuxian` v1 已保存工程里嵌入的模型、符号、探针及多套仿真和波形配置。工作台内本机项目 URL 只识别当前本机工程 ID；文件重开目前总建立独立副本。 | 保持 v1 兼容，补“检查并分享”和导入后复现；不把本机链接当分享链接。 |
| AI 连接固定目录 | 启动器已经按自身位置找运行文件。真正失效的是导出的 MCP 命令和参数含当前运行时、工作台脚本和连接描述文件的绝对路径；高级桌面连接设置以及自建库也有按安装目录保存的数据；它们需要分别处理。 | 先做当前电脑自动生成和诊断，再做稳定入口；既有高级桌面会话只做显式重新关联。 |

取舍：只统一浏览器地址，开发量小，但换浏览器资料仍可能丢视图；每次只打开一个文件，分享容易，但自动保存和最近项目仍弱。建议采用**本机项目库 + 单工程文件**，兼顾日常恢复和跨机器交付。保留便携 ZIP；安装程序、云账号、多人实时协作不列为本轮依赖。

## 2. 计划交付后的使用方式

1. **首次启动：** 启动器打开工作台。没有自己的工程时显示“打开工程 / 新建工程”，示例按需打开；服务正在读取工程时显示“正在恢复”，不闪现并自动保存一个默认示例。
2. **每天继续：** 退出前保存最后编辑的工程，下次直接恢复原工程和可恢复的视图；工程路径不可用时给出“重新定位 / 从备份恢复”。偏好中的默认启动行为是“继续上次工程”，可切换为“最近工程”。
3. **发给同事：** 从工程菜单“分享工程文件”，预览要带走的模型与符号以及缺失项；同事解压软件，从顶部“打开工程”打开文件，运行同一套仿真配置。
4. **连接助手：** 进入 设置 → AI 连接，选 Codex、Cursor 或 DSH；自动查找，找不到可手选程序。按照“生成或安装配置 → 检查客户端工具 → 核对当前工程”完成连接；错误提示指出该修哪一步。绘图和仿真不要求连接 AI。

### A · 本机工程库和保存协议（P0，存储工作树）

文件所有权：新建 `server/project-repository.ts`、`server/project-repository-middleware.ts`、`tests/project-repository.test.ts`；存储工作树负责 `scripts/serve-local.mjs`、`vite.config.ts` 接线。先定义接口，再让应用工作树并行联调。

- [ ] 定义 `bootstrap`、`read(id)`、`save(id, expectedRevision, project)`、`select(id)` 的请求和失败状态。本机服务只接受当前工作台的同源请求；通过工程 ID 查找文件，API 不接受任意文件路径。
- [ ] 默认 Windows 位置为 `%LOCALAPPDATA%\Fuxian`，让设置与启动器可查看；若之后提供自选数据目录，先验证权限和已有库身份，切换失败时继续使用原有目录。安装目录与用户存储相互独立。开发和一次性测试显式使用隔离数据目录。
- [ ] 分开存工程文件和索引，索引维护最近、最后打开、修订和更新时间。写入用同目录临时文件、校验、原子提交及上一份可恢复版本；崩溃发生在工程与索引之间时可从文件重新对账。切换工程仅更新选择；同工程并发写入校验修订，冲突保留两份，明确交给用户选。两个服务进程可能共用同一数据目录；用操作系统级单写入锁或支持跨进程事务的存储，不能只用进程内队列。验收覆盖不同端口并发保存。
- [ ] 验收：写入后重启并重新读取相同 ID；模拟权限不足、磁盘写入失败和异常中断，旧版本仍可恢复；两个页面并发保存返回冲突。`npx --no-install tsx --test tests/project-repository.test.ts` 应全部通过；仅在实际调用本机端点的集成测试通过后交接。

## 4. 集成、升级和出包门槛

- 前置：将实际启动方式、浏览器/站点来源以及“重开不见”的复现场景写成脱敏证据。先在合成项目和旧版升级测试中验证，用户现有 3032 工程和对话无需拿来测试。A/B/C 可并行准备，按 A 接口 → B 恢复 → C 集成验证；D/E 分别并行，F 待前两版场景稳定后动手。每个任务单独提交，通过验证再合入发布工作树。
- 完整回归运行 `npm ci`、`npm test`，记录基线与实测结果。用同一组大工程比 v0.30.5 的启动恢复、项目切换、缩放和侧栏拖动；冷启动与热切换分别记录，否则数据不比较；普通缩放与侧栏动作不读写持久库、不触发全工程序列化或自动走线；保留 v0.30.5 仿真精度与点数。
- 用旧版工程升级、全新 Windows 用户、第二台断网电脑各走一遍。版本升级先以新目录解压，不覆盖旧版；旧版回退时打开升级前保留的数据，升级后新增或编辑的工程先导出 v1 文件再交给旧版，不能让旧版直接写新索引；首次看到未迁移数据要有明确恢复入口。测试以可复现样例验证写入/迁移失败后旧数据仍可访问。只有通过该门槛才标记 GitHub Release 为正式版。
- 发布交付：Windows ZIP、SHA-256、一个公开的可离线试跑 `.fuxian` 示例、图示《首次打开 / 迁移旧项目 / 接入 AI》指南；安装目录和数据位置清楚区分，记录实际通过的客户端版本和已知限制。
